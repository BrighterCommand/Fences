Fences

4. Port upstream's xunit v3 and Microsoft Testing Platform v2 test setup

Date: 2026-10-12

Status

Accepted

Amended 2026-10-18 (after PR #51 merged): divergence 5, a coverage report directory per TFM. It replaces the "Why keep the shared HTML report directory?" reasoning below. PR #19 is closed in favour of it.

Context

Fences' tests run on xunit v2 and VSTest, and coverlet 6.0.4 collects and enforces coverage. Upstream Polly moved to xunit v3 and Microsoft.Testing.Platform (MTP) v2 in App-vNext/Polly@1a80392b. Since then, every upstream commit that touches tests, build scripts, coverage or Stryker assumes the new setup. Fences cannot port those commits one at a time without re-engineering each one. Coverlet's figures are also not reproducible across runs (#14), and on Windows the coverage gate never sees net481 at all.

Scope

Parent requirement: specs/001-port-xunit-v3/requirements.md

In scope

  • FR-1: every test project becomes an MTP executable on xunit v3, and global.json selects MTP as the dotnet test runner.
  • FR-2: the package and tool changes in the requirement's closed table, at the current version under its major-version and Dependabot rules.
  • FR-3: eng/Test.targets tells the CodeCoverage extension to write one Cobertura file per project per TFM, net481 included on Windows.
  • FR-4: a new Cake task, __GenerateCoverageReports, runs the reportgenerator tool once per coverage file. It runs before the threshold check, so the reports survive a failing check.
  • FR-5: a new Cake task, __VerifyCoverageThresholds, decides pass or fail per project per TFM. It carries one Fences divergence: a missing coverage file fails the check.
  • FR-6: the Specs threshold rises to 96,95,93. A remaining gap is investigated as a porting omission first.
  • FR-7: upstream's test changes are applied to Fences' own files, rebranded, with upstream's test names.
  • FR-8: upstream's four src/ edits and the polyfill deletion are ported, with no public API change.
  • FR-9: eng/stryker-config.json selects the MTP runner. The mutation workflow sets MinVerSkip on CI.
  • FR-10: the GitHub reporter replaces the VSTest loggers. The existing upload step keeps publishing artifacts/coverage-reports.
  • FR-11: the contributor documentation moves to dotnet test --project, and to xunit v3's --filter-class in place of FullyQualifiedName~.
  • FR-12: a separate commit ports f35bc00d's three Specs edits.
  • FR-13, FR-14, FR-15: delivery order, the mutation baseline and the reproducibility evidence. The Implementation Approach lists all three.
  • NFR-1 to NFR-6: no new analyser warnings, no public API change, no src/ behaviour change, a build-duration bound, no skipped tests, and in-process tests only.
  • NFR-7: the port matches upstream, rebranded, except for the closed list of four divergences that this ADR records. The 2026-10-18 amendment adds a fifth.

Out of scope

  • Porting any other upstream commit. The sync process is ADR 0003. The non-Specs half of f35bc00d has already been ported (#44).
  • Dependency changes outside FR-2, for example Cake.Sdk or Microsoft.Extensions.*. Fences tracks these with its own Dependabot setup (ADR 0003 D5).
  • A separate HTML coverage report for each TFM. The parent requirement excludes it, and no ADR covers it.
  • Renaming test methods, changing Stryker's scope or thresholds, and changing TFMs. The parent requirement excludes these, and no ADR covers them.
  • The root cause of the mutations-core hang (#46), and any external coverage service. The parent requirement excludes both.
  • Public API changes. None is expected. If one is needed, ADR 0003 D7 governs it.

Fences differs from upstream on every row of that table. So every later upstream commit that edits a test helper, a Cake task or eng/Test.targets is a re-engineering task, not a rebrand. ADR 0003 D7 makes rebranding the norm. Upstream's own f35bc00d shows the cost: #44 ported its build-props half, but its Specs half edits three files that only exist after 1a80392b, so that half cannot land.

The coverage gate also has two gaps. Coverlet's figures vary between runs on the same commit, which #14 records. A TFM whose coverage is never collected looks the same as a TFM that passed, because nothing lists the TFMs that should have been checked. On Windows, that gap is permanent for net481.

The forces

  • ADR 0003 D7 says porting rebrands and does not redesign. A Fences-shaped redesign would make every later upstream commit to these files a manual merge.
  • NFR-7 closes the list of divergences at four. Any other difference from upstream needs the requirements to change first.
  • FR-2 authorises dependency changes for this port only. ADR 0003 D5 skips dependency bumps by default, and CLAUDE.md's verification gate 6 is waived only for FR-2's rows (C-3).
  • C-4 says thresholds are never lowered. C-6 keeps the TFMs as they are. C-7 keeps Stryker on net10.0, Debug, with thresholds of 100.
  • #14 shows that a TFM which silently drops out of coverage hides a regression. Upstream's check skips a missing file or directory.
  • The build job has a 20-minute timeout (.github/workflows/build.yml:27). Collecting net481 coverage on Windows adds work inside that limit (NFR-4).
  • Upstream's Cake scripts in Fences differ from the 1a80392b parent only by rebranding, so the upstream diff applies cleanly. The same is true of eng/Test.targets.
  • build.ps1 passes only --target, --configuration and --verbosity to Cake. It cannot run a single task without that task's dependencies.

Decision

Fences adopts upstream's xunit v3, MTP v2, coverage and Stryker setup from App-vNext/Polly@1a80392b, rebranded, and diverges from it only by the four divergences that NFR-7 lists, plus the fifth that the 2026-10-18 amendment adds.

The port lands as one upstream-SHA commit that applies 1a80392b as written, with names rebranded. One or more Fences-only commits follow it. These make the threshold check fail on a missing coverage file, update the contributor documentation, and close any Fences-specific coverage gap. A final commit ports f35bc00d's Specs edits. Everything else matches upstream, including the shared HTML report directory, the threshold-message format and the failure modes.

These invariants follow from the diagrams:

  • Reports never depend on the threshold check. Cake runs Build's dependencies in the order they are declared, and __GenerateCoverageReports is declared before __VerifyCoverageThresholds. A failing check therefore leaves every HTML report and every job-summary section already written.
  • A failing test stops the build at __RunTests, before any report is generated. Upstream does the same, and FR-4 accepts it.
  • No TFM can drop out silently. The project file's evaluated TargetFrameworks sets which TFMs the check expects. The files that happen to exist do not.
  • Comparisons use the unrounded value. A figure of 99.995 against 100 fails, even though it prints as 100%.
  • Every violation is reported before the build fails. Rows 2 and 4 are the exceptions: they throw at once, as upstream does.
  • The test project's .csproj stays the single source of truth for both the threshold triple and the TFM list.
  • Requirements discharged: FR-3, FR-4, FR-5, FR-9, FR-10, AC-10, AC-11, AC-12, AC-13, AC-14, AC-15, AC-22.

Technology Choices

Why port verbatim rather than redesign? ADR 0003 D7 makes "rebrand, don't redesign" the rule for every port. Fences' cake.cs and eng/Test.targets differ from the 1a80392b parent only by rebranding. A verbatim port keeps them that way, so the next upstream commit to these files also applies as a rebrand. Any redesign, however small, becomes a merge conflict in every later sync. NFR-7 therefore limits Fences to four divergences, each with a reason the upstream shape cannot meet.

Why Microsoft CodeCoverage rather than coverlet 10 or coverlet.collector? Upstream chose Microsoft CodeCoverage, and the port follows upstream. On its own merits, MTP needs a collector that runs as an MTP extension. coverlet.msbuild hooks VSTest's dotnet test targets, and those targets do not run under the MTP runner. Staying on coverlet would mean either staying on VSTest, or adopting a coverlet MTP integration that upstream does not use. Both keep Fences off upstream's shape. The coverlet.msbuild 10.x bump (#6) and PR #19's fixes are VSTest-era repairs. Neither addresses #14's non-determinism at its source.

Why does [ExcludeFromCodeCoverage] still work without a settings file? Upstream passes no --coverage-settings: CoverageRunSettings is never set, so eng/Test.targets omits the flag. Upstream relies on Microsoft CodeCoverage's default attribute exclusions. That list contains System.Diagnostics.CodeAnalysis.ExcludeFromCodeCoverageAttribute, along with DebuggerHiddenAttribute, DebuggerNonUserCodeAttribute, CompilerGeneratedAttribute and GeneratedCodeAttribute. Fences' 13 files that use the attribute match upstream's file for file, so they need no setting. The extra default exclusions can move figures relative to coverlet. That is one reason why the thresholds are re-measured, not assumed.

  • FR-3 (the [ExcludeFromCodeCoverage] bullet), FR-6, AC-6, AC-17.

Why fail on a missing coverage file when upstream skips it? Upstream's check iterates over the files that exist. A TFM whose run wrote nothing therefore reports nothing, which looks the same as success. #14 describes exactly that failure. The divergence is a few lines in one task, with a code comment that points to this ADR. It stays easy to see during later syncs, and the rest of the task remains upstream's text.

  • FR-5 (missing coverage file boundary), NFR-7 item 1, AC-14.

Why ask MSBuild for the built TFMs, rather than list them in cake.cs? The .csproj already knows its TFMs, including the Windows-only net481 condition. dotnet msbuild -getProperty:TargetFrameworks evaluates that condition on the current OS. A list in cake.cs would copy that knowledge and drift the first time a TFM changes. Reading artifacts/bin would tie the check to the build output layout, and would only report what was built, which is the condition being checked. One MSBuild evaluation per project costs seconds, which is small against NFR-4's bound.

Why a report directory per TFM? (Amendment, 2026-10-18.) Upstream writes every TFM of a project into one directory, so each run overwrites the last, and the HTML a reviewer opens shows only one TFM. The original decision kept upstream's shape, arguing that the check output and the CI job summary already show every TFM. In practice, the HTML is where a reviewer finds the uncovered lines, and a TFM-specific gap (the kind #14 chases, and net481's first appearance) is exactly the case it hid. PR #19 fixed this overwrite for coverlet, and #51 dropped that fix. Divergence 5 restores it on MTP: __GenerateCoverageReports passes <Project>/<tfm>/ as -targetdir. That is one path segment in one task, so a later upstream change to the task still applies as a rebrand plus that segment. The CI artefact already uploads all of artifacts/coverage-reports, so build.yml does not change. Each TFM's job-summary section reads that TFM's own SummaryGithub.md.

  • FR-4 (shared HTML directory boundary), FR-10, AC-8.

Why keep upstream's message format, rounding and XML-load failure? These are upstream's text. Changing them would be a divergence that buys only cosmetic precision. The comparison already uses the unrounded value, so a figure printed as 100% that is below 100 still fails. An empty or malformed file still fails the build at XDocument.Load, before any later file is read.

  • FR-5 (rounding and unreadable-file boundaries), AC-13, AC-15.

Why is the local MinVerSkip step documentation only, and why record it as a divergence? Upstream works around stryker-net#3094 only in its CI workflow. A coded local workaround in cake.cs would change a file that must track upstream. A note in CONTRIBUTING.md and .agent_instructions/testing.md changes no upstream-tracked file. It is still a difference in how Fences tells contributors to run an upstream-shaped process. This ADR therefore records it as divergence 3, so the next sync after stryker-net#3094 is fixed knows to remove it. FR-11's other documentation changes only describe Fences' files as they are after the port. They are not divergences.

  • FR-9 (local runs), FR-11, NFR-7 item 3, AC-23.

Why keep upstream's test names? Upstream's two new Core.Tests methods already follow Member_Scenario_Outcome. Its new Specs methods use snake_case, which matches the Specs project's legacy style. If the names change, f35bc00d's hunks no longer land on methods of the same name, and neither will any later upstream edit.

  • FR-7, FR-12, AC-20, AC-28.

Why --filter-class replaces --filter "FullyQualifiedName~…"? Under MTP, xunit v3 does not accept VSTest filter expressions. It provides --filter-class, --filter-method, --filter-namespace, --filter-trait and --filter-query. --filter-class with leading and trailing wildcards gives the substring-like match that the documented commands intend. dotnet test passes the option through to the test host:

dotnet test --project ./test/Paramore.Fences.Core.Tests --filter-class "*CircuitBreaker*"
dotnet test --project ./test/Paramore.Fences.Core.Tests --framework net10.0 --filter-class "*CircuitBreaker*"

The documented FullyQualifiedName~CircuitBreakerTests matches no test today. No class or namespace in Paramore.Fences.Core.Tests contains that substring. VSTest only warns about this. MTP fails a run that executes zero tests, so a literal translation would fail AC-26. *CircuitBreaker* matches every class in the Paramore.Fences.Core.Tests.CircuitBreaker namespaces, which is what the command intends. --filter-query would also work, but its path syntax is harder to read in a contributor guide.

  • FR-11, AC-26, Open Question 5.

How does the threshold check run on its own? AC-13, AC-14 and AC-15 edit coverage files after a test run, then run only the check. Running --target=__VerifyCoverageThresholds alone would first run its dependency __RunTests, which rewrites the edited files. Cake's existing --exclusive option runs a target without its dependencies. Cake.Sdk's generated command line declares --exclusive|-e and calls UseExclusiveTarget() when it is set. build.ps1 does not pass extra arguments through, so verification calls the script directly, in the same form build.ps1 uses:

dotnet cake.cs -- --target=__VerifyCoverageThresholds --exclusive

This command needs no change to build.ps1 or cake.cs, so it is not a divergence. Before the AC runs, --dryrun added to the same command confirms that only __VerifyCoverageThresholds would execute. If the pinned Cake.Sdk does not honour --exclusive, the fallback is a local, uncommitted edit that removes .IsDependentOn("__RunTests") from the check task. This is the same kind of experiment as AC-10's and AC-12's temporary <Threshold> edits.

Consequences

Positive

  • Later upstream commits that touch tests, Cake, eng/Test.targets or Stryker port as rebrands. The deferred half of f35bc00d lands in the same PR.
  • Coverage is collected and enforced for every built TFM, net481 included. A missing TFM fails the build and does not pass silently.
  • Coverage reports and job-summary sections survive a failing threshold check, so the project that needs attention is always inspectable. This replaces PR #19's gate fix.
  • The coverage pipeline becomes plain Cake code that can be read and tested in place. It no longer depends on coverlet's MSBuild integration and an inline Roslyn task.
  • Upstream's added tests and the Specs threshold of 96,95,93 raise Fences' coverage floor.

Negative

  • The HTML report holds only the last TFM processed. Per-TFM detail is in the coverage files, the threshold output and the CI job summary, not in a browsable report.
  • Divergence 1 is code that each later sync touching __VerifyCoverageThresholds must carry forward by hand. The code comment marks it, but it is still a merge point.
  • The threshold check now runs one MSBuild evaluation per test project, which adds a few seconds to every build.
  • Contributors must learn dotnet test --project and xunit v3's filter options. The VSTest commands they know stop working.
  • Stryker 5 on MTP needs MinVerSkip on CI as a workaround for an open Stryker issue. Local runs may need the same.

Risks and Mitigations

Risk Mitigation
net481 coverage is checked for the first time, and it falls short of 100 or 96,95,93 on Windows. FR-6: investigate as a porting omission first. Only a Fences-specific gap gets a Fences-only test or a documented exclusion (divergence 4). Thresholds are never lowered (C-4).
Microsoft CodeCoverage is also non-deterministic (A-1), for example at src/Paramore.Fences.Core/Utils/Pipeline/ComponentDisposeHelper.cs:30. FR-15's three runs measure it. If figures vary, #14 stays open with the evidence. That does not block the merge while CI's threshold checks pass.
Stryker 5 with MTP changes the mutations-core hang (#46). FR-14's rerun path, then the like-for-like local fallback, with #46 updated. A hang that neither path resolves fails FR-14.
stryker-net#3094 also breaks local mutation runs. FR-9 measures it. If it does, divergence 3 documents MinVerSkip=true, and cake.cs stays upstream's.
Losing per-TFM HTML hides a TFM-specific gap from reviewers. Resolved by divergence 5 (amendment, 2026-10-18): each TFM keeps its own report directory. The threshold check still prints figures for every TFM, and a short TFM still fails the build.
Collecting coverage on net481, plus Stryker 5, pushes the Windows build job toward its 20-minute timeout. NFR-4 records the measured times and the cause if the 20% bound is exceeded. Changing build.yml's timeout is not in NFR-7's list, so it would need the requirements amended first.
The pinned Cake.Sdk does not honour --exclusive, so the isolated check cannot run. The --dryrun pre-check finds this before the AC runs. The fallback is a local, uncommitted edit, so no script changes.
A current version under FR-2 is a higher major than upstream's (for example MTP 3.x). FR-2 pins to upstream's major and records an open item in the PR body. A maintainer decides on a follow-up.

Alternatives Considered

1. Do nothing: keep xunit v2, VSTest and coverlet 6.0.4. This option costs nothing now. It is rejected because every later upstream commit to tests or build scripts becomes a re-engineering task, which contradicts ADR 0003 D7. The deferred half of f35bc00d stays blocked. #14's non-determinism and the unchecked net481 coverage stay as they are.

2. Move to coverlet 10, or to coverlet.collector, on xunit v2. This is the path of #6 and PR #19. It would fix the report-on-failure bug and might reduce coverlet's variance. It is rejected because it moves Fences further from upstream's shape, not closer. Every 1a80392b-dependent upstream commit would still need re-engineering. The coverlet version would also become a Fences-only dependency choice outside FR-2. The VSTest host itself is suspected in the varying test count and the #46 hang (A-6), and this option keeps it.

3. Port only part of 1a80392b, for example xunit v3 and MTP, while keeping coverlet's gate. This option looks smaller. It is rejected because the parts depend on each other. Coverlet's MSBuild gate does not run under MTP. Upstream's test/ changes assume xunit v3 and its new Cake tasks. Upstream's Stryker suppressions and added tests exist because of the collector change. A partial port is a redesign that every later sync pays for, and it breaks NFR-7's closed divergence list.

4. Redesign the coverage pipeline the Fences way: per-TFM HTML, one MSBuild target per concern, and named errors for every failure mode. This option would give a cleaner local design: per-TFM HTML reports, a named error for an unreadable file, and exact-decimal messages. It is rejected because each of those is a divergence that NFR-7 does not allow, and each becomes a merge conflict in later syncs. Only the missing-file failure earns its divergence, because it closes the gap that #14 describes. The other improvements are cosmetic next to the cost of drifting from upstream.
